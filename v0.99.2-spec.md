# v0.99.2 — Multi-device merge (engineer spec)

**Release 3 of 3 in the Sync Run. This is the one schema change: v12 → v13.**
Ships the honest multi-device story the first two releases set up: edits made
on two devices both survive, deletions propagate instead of resurrecting, and
the conflict modal — now rare — tells the user *what* differs.

You are implementing this blind from this document. Read `North_Star_V2.5.md`
and `CLAUDE.md` first; they govern voice, tokens, and invariants and override
anything here they contradict. Where this spec is silent, match the surrounding
code. Where it is explicit, follow it exactly.

Predecessors, already merged and not to be re-litigated:
`v0.99.0-2-spec.md` (the base + reconciliation addendum — the C-conventions and
A-items referenced below live there), v0.99.0 (`235c179`), v0.99.1 (`1a7faa2`).

## 0. The problem, precisely

Current `mergeStates` (`src/lib/sync.js`) is **blunt local-wins**:

- id-keyed collections (`items`, `routines`, `programs`) union by id, **local
  always wins** on a shared id — a stale local copy overwrites a newer remote edit.
- `history` unions by date-key, local wins.
- scalar/object fields: **remote wins** (`...remote` spread).
- **No deletion handling.** A piece deleted on Device A reappears the moment
  Device B (which still holds it) syncs — the id is "remote-only" from one
  side and gets re-added. Deletions resurrect. This is the headline bug.

Current conflict detection (`doSync` in `useEtudesState.js`) only inspects
`items`, fires a modal on any structurally-different shared id, and the modal
(`SyncConflictModal`) shows bare counts (`localCount` / `remoteCount`), not
which pieces. `routines`, `programs`, `history`, `settings`, and the reflection
surfaces get no conflict handling at all — they merge bluntly and silently.

v0.99.2 replaces blunt-wins with **per-entity last-writer-wins (LWW) keyed on
`updatedAt`**, adds **tombstones** so deletions win when they are the newer
event, brings **settings + history** into the merge (A9), and makes the
now-rare modal **informed**.

## 1. Hard invariants — do not break

From the sync-hardening trilogy and v0.99.0/.1. Grep for each before you touch
the file it lives in.

1. **`signInEpoch`, not `user`, gates the conflict-check effect.** The `doSync`
   effect deps are `[signInEpoch]`. Do not change to `[user]`.
2. **`structurallyEqual` (not `JSON.stringify`) for overlap detection**, and it
   **ignores `updatedAt`** via `IGNORED_EQUALITY_KEYS`. You will add more
   `updatedAt`-bearing entities; keep them equal-when-only-timestamp-differs by
   leaving `updatedAt` in the ignore set. (It is matched by key name at every
   object depth, so one entry covers all entities. Verify this still holds after
   you add per-entity `updatedAt`.)
3. **`applyingCloudRef` guards stamping and dirty-tracking.** Applying cloud
   state must never stamp `updatedAt` and never mark the journal dirty. The
   dirty effect at `useEtudesState.js:132` already early-returns on
   `applyingCloudRef.current`; your stamping choke-points must sit on the
   user-mutation path only, so a cloud apply (which calls the raw setters in
   `applyCloudStateRef`) never routes through them.
4. **v0.99.1 Drive continuity is untouched.** `driveReady` reactive state,
   metadata-only Drive journal (`includeBlobs:false`), the A1 coverage
   escalation, device-local `driveConnectedAt`/`driveAccountEmail`, the
   `driveBlobHashes` content-hash skip — none of this changes. Drive journal
   stays metadata-only; `deletions`/`reflectionMeta` are metadata and ride it
   normally.
5. **iOS gesture invariants** (synchronous `requestDriveTokenInteractive`, eager
   `prepareDriveAuth`, GIS preload) — not in scope, do not perturb.
6. **`mapSyncError` (v0.99.0):** any new sync failure surface routes through the
   mapped copy, never a raw Supabase/fetch string.
7. **One shared `mergeStates` (C3).** Do not fork a second merge function for
   the boot path vs the debounced path. Both use the same LWW `mergeStates`.

## 2. Schema v13 — exact additions

Bump `SCHEMA_VERSION` to `13` in `src/constants/config.js` (leave `APP_VERSION`
to the release commit). All additions are **additive**; a v12 blob loads under
v13 with the defaults below. Add each to the migration (`src/lib/migrations.js`)
and the completeness surfaces in §6.

### 2.1 Per-entity `updatedAt` (epoch ms)

Stamped on **user mutation only** (§3). Applies to:

| Collection | Field | Notes |
|---|---|---|
| `items[]` | `item.updatedAt` | |
| `routines[]` | `routine.updatedAt` | |
| `programs[]` | `program.updatedAt` | |
| `freeNotes[]` | `note.updatedAt` | **already exists** (schema v11) — reuse, do not duplicate. |
| `history[]` | `entry.updatedAt` | day/week/month entries. |

Migration: a v12 entity with no `updatedAt` → **`updatedAt: 0`** ("unknown /
oldest"). Do **not** backfill to migration-time — that would make two upgraded
devices tie. `0` means any real post-upgrade edit deterministically wins.

### 2.2 `deletions` (tombstones) — top-level array

```
deletions: Array<{ type: 'item'|'routine'|'program'|'note', id: string, deletedAt: number }>
```

Default `[]`. Lifecycle in §4. Not per-entity — one flat top-level list. History
entries are **not** tombstoned (they are keyed by date and never user-deleted in
a way that must propagate; leave them out of scope — see §8).

### 2.3 `reflectionMeta` — top-level object

The three reflection surfaces are singletons with no id to stamp:

```
reflectionMeta: {
  daily?: { updatedAt: number },
  week?:  { updatedAt: number },
  month?: { updatedAt: number },
}
```

Default `{}`. Stamped when the corresponding surface is edited (§3). Used for
LWW on `dailyReflection`, `weekReflection`, `monthReflection` (§5.4).

### 2.4 `settings.updatedAt`

Stamp on any user settings change. Default (missing) → treated as `0`. Used for
LWW on the whole `settings` object (§5.4). `settings.updatedAt` itself is
excluded from `structurallyEqual` (it is already covered by the `updatedAt`
ignore key).

## 3. Stamping choke-points (A6)

Add one pure helper in `src/lib/sync.js` (exported, unit-tested):

```
export function stampChanged(entity) { return {...entity, updatedAt: Date.now()}; }
```

Route **every user mutation** of a stamped collection through it, at the reducer
site in `useEtudesState.js`. The rule: *if a set of fields the user can see and
edit changes, `updatedAt` moves.* Concretely, stamp in the updater for:

- items — every `setItems` updater that changes item content (add, edit fields,
  edit spots, stage change, tempo log, notes, pdf attach/detach, score links…).
  A `setItems(prev => prev.map(i => i.id===id ? stampChanged({...i, ...patch}) : i))`
  shape. Timer-only fields (`itemTimes`, live session time) are **not** item
  content and must **not** stamp the item (they already sync via the v0.99.0
  boundary/heartbeat path).
- routines, programs — same shape on their edit/add reducers.
- freeNotes — `saveFreeNote` already stamps `updatedAt: Date.now()`; leave it,
  optionally reroute through `stampChanged` for consistency.
- reflections — when `dailyReflection` / `weekReflection` / `monthReflection`
  change by user edit, also write `reflectionMeta[scale].updatedAt = Date.now()`.
- settings — when the user changes a setting, set `settings.updatedAt = Date.now()`.

**Guard:** none of these fire during a cloud apply, because
`applyCloudStateRef.current` sets state via the raw setters, not these reducers.
Do not add stamping inside `applyCloudStateRef`. Add an assertion in review:
grep every producer that writes `updatedAt` and confirm none is reachable from
`applyCloudStateRef`.

**Deletion choke-points:** every user delete must append a tombstone *and*
remove the entity, in the same reducer:

- `deleteItem(id)` → `setDeletions(d => pushTombstone(d, {type:'item', id, deletedAt:Date.now()}))` + remove from items.
- same for routines (`type:'routine'`), programs (`type:'program'`), notes (`type:'note'`).

`pushTombstone` (pure, in `sync.js`) appends and prunes (§4).

## 4. Tombstone lifecycle (A10)

Pure helpers in `sync.js`, unit-tested:

- **`pushTombstone(deletions, entry)`** — append, then prune. Prune rule:
  drop entries older than **90 days** (`deletedAt < now - 90*24*3600*1000`),
  then if still over **500**, keep the **500 most recent** (FIFO by `deletedAt`).
  Log nothing; this is silent housekeeping.
- **`applyTombstones(collectionById, deletions, type)`** — given a merged
  id-keyed collection and the merged tombstone list, remove any entity whose id
  has a tombstone of matching `type` with **`deletedAt > entity.updatedAt`**.
  (A re-created entity with a newer `updatedAt` than the tombstone survives —
  this is why the timestamp comparison, not mere presence, is the rule.)
- **Tombstone merge:** union both sides' `deletions` by `${type}:${id}`, keeping
  the **newest `deletedAt`** on collision, then prune once.

Ordering in `mergeStates` (§5) is: LWW-merge each collection → merge+prune
`deletions` → `applyTombstones` to each collection. Deletion-wins-over-stale and
recreate-wins-over-old-tombstone both fall out of the `deletedAt > updatedAt`
comparison.

## 5. The new `mergeStates` (C3)

Rewrite `mergeStates(local, remote)` in `sync.js`. Keep the signature and the
legacy-tolerance (`history` may be a non-array on corrupt state). Per field:

### 5.1 id-keyed collections — LWW then tombstones
`items`, `routines`, `programs`: union by `id`; on a shared id keep the entity
with the **greater `updatedAt`** (missing → `0`; exact tie → keep local, stable).
Then `applyTombstones` with the merged `deletions` and the matching type.

### 5.2 freeNotes — LWW then tombstones
Same as 5.1, type `'note'`.

### 5.3 history — LWW by entry
Union by the existing `historyKey`; on collision keep the greater `updatedAt`
(missing → `0`, tie → local). No tombstones (§8).

### 5.4 singletons — LWW by side-timestamp
- `settings`: keep the side whose `settings.updatedAt` is greater (missing → 0,
  tie → local). Merge as a **whole object** — do not field-merge settings.
- `dailyReflection` / `weekReflection` / `monthReflection`: for each scale, keep
  the side whose `reflectionMeta[scale].updatedAt` is greater (missing → 0, tie
  → local). Carry the winning side's `reflectionMeta[scale]` into the result.

### 5.5 `deletions`
Merged + pruned per §4 and returned in the result.

### 5.6 everything else — unchanged
`itemTimes`, `pieceRecordingMeta`, `refTrackMeta` keep `mergeObj` (local wins per
key — these are additive maps). `workingOn` stays the set-union. Session-local
day state (`todaySessions`, `dayClosed`, `loadedRoutineId`, `warmupTimeToday`,
`restToday`) keeps the current `...remote`-wins default. Do not change these
without a stated reason in your report.

Result must contain **every key** the current `mergeStates` returns plus
`deletions` and `reflectionMeta`. A dropped key silently wipes that slice on
every merge — this is the highest-risk mistake in this file.

## 6. Completeness checklist (A7-ii) — do this or the keys vanish

Every new v13 key (`deletions`, `reflectionMeta`, per-entity `updatedAt`,
`settings.updatedAt`) must be threaded through **all** of:

1. `coldState` memo (`useEtudesState.js:220`) — add `deletions`, `reflectionMeta`
   to the object and the dep array.
2. `applyCloudStateRef.current` (`:618`) — set `deletions`, `reflectionMeta` from
   the incoming state with defaults (`s.deletions||[]`, `s.reflectionMeta||{}`).
   `updatedAt`/`settings.updatedAt` ride inside the entities/settings already.
3. `syncStateRef` (`:224`) — inherits from `coldState`; confirm it carries the
   new keys.
4. Export payload — `buildFullJournalPayload` (`src/lib/journalPayload.js`) must
   emit `deletions` and `reflectionMeta` (both `includeBlobs` modes; they are
   metadata). Confirm the Drive metadata-only journal carries them.
5. `applyJournalPayload` (same file) — read them back with defaults on restore.
6. Migration (`migrations.js`) — `migrateImport` / per-collection migrators set
   defaults and stamp `updatedAt:0` on un-stamped v12 entities; bump the schema
   gate to 13.
7. `structurallyEqual` — confirm `updatedAt` (and `settings.updatedAt`) stay
   ignored; add `deletions`/`reflectionMeta` to the equality *only if* they
   should count as content for conflict detection — **they should not** (a
   tombstone list difference is not a user-facing conflict). Add them to
   `IGNORED_EQUALITY_KEYS` if their presence would false-positive the overlap
   check, or exclude them from the compare set. State your choice in the report.

Grep-audit: after wiring, `grep -n "deletions\|reflectionMeta" src/` should show
each of the seven surfaces above. A key present in `coldState` but missing from
`applyCloudState` (or vice-versa) is the classic silent-drop bug.

## 7. Informed conflict modal (A9)

With LWW, the common multi-device case resolves **silently** — no modal. Extend
detection and keep a modal only for the genuine concurrent-edit case, now
**informed**.

### 7.1 Detection scope (widen beyond items)
The overlap test currently runs only on `items`. Extend it to compute, across
`items` + `routines` + `programs` + `freeNotes`, the set of **shared ids whose
two sides are not `structurallyEqual`** — i.e. genuinely divergent entities.
Call this the *divergence set*. Settings and reflections: include a divergence
flag per singleton (settings differ ignoring `updatedAt`; a reflection scale
differs). History is not conflict-surfaced (LWW silent).

### 7.2 When the modal fires
- **No divergence set** (only unique-to-each-side entities, or all shared
  entities equal): silent LWW merge + push, exactly as the current no-overlap
  branch. This must stay the overwhelmingly common path.
- **Divergence set non-empty AND both sides carry a real `updatedAt` on the
  divergent entities**: **auto-resolve by LWW silently** — newest edit wins per
  entity. This is new: two devices that each edited *different* fields of the
  same piece at different times no longer nag. Only escalate to the modal when
  LWW cannot pick, i.e. an exact `updatedAt` tie on a divergent entity, **or**
  when either side's divergent entity has `updatedAt:0` (un-stamped v12 legacy
  data, where LWW would be a coin-flip on real content). Those are the cases a
  human should see.

Pick the escalation predicate deliberately and state it in your report; the
above is the required default. The point of the release is *fewer, honest*
modals, not zero.

### 7.3 What the modal shows (informed)
`SyncConflictModal` (`src/components/modals.jsx`) currently renders counts.
Change it to name the divergent entities: e.g. *"Edited on both devices:
Chopin Op. 25/11, Bach BWV 847, Morning routine."* Cap the list (show first ~5,
"+N more"). Keep the three actions but relabel to reflect LWW:
- **Merge (keep newest of each)** — runs LWW `mergeStates` (the default, IKB).
- **Keep this device** — push local wholesale.
- **Keep cloud** — apply remote wholesale.

Voice: declarative, ≤2 sentences of body, no exclaim/emoji, tokens only. Match
the existing modal's structure and the NS reference strings.

## 8. Out of scope (do not do)

- History-entry tombstones / per-reflection conflict modals (history is LWW-
  silent; reflections escalate only on tie/legacy).
- Field-level settings merge (settings is whole-object LWW).
- Any Drive change. Any auth/gesture change. Any UI beyond the conflict modal
  copy + the entity-name list.
- Real-time / CRDT / operational-transform machinery. LWW-by-`updatedAt` is the
  whole model.
- A background tombstone-GC timer — pruning happens inline in `pushTombstone`.

### Two-device device matrix (for the reviewer / Alain, on production)
1. **Different pieces edited on A and B** → both survive, no modal.
2. **Same piece, different times, different fields** → newest edit wins silently,
   no modal.
3. **Delete on A, B still has it, both sync** → piece stays deleted (does not
   resurrect). Reverse direction too.
4. **Recreate after delete** → a piece re-added on B with a newer `updatedAt`
   than A's tombstone survives.
5. **Exact concurrent edit (contrived tie / legacy `updatedAt:0`)** → informed
   modal lists the piece(s); each action resolves correctly.
6. **Settings changed on both** → newest wins; reflections likewise per scale.
7. **v12 → v13 upgrade** on a device with existing data → loads clean, first
   cross-device sync resolves by whoever edits first post-upgrade.
8. **Regression:** token-refresh 60-min soak still fires no modal (invariant 1);
   Drive backup unaffected (invariant 4).
