## A1 — Fold in the refTrack backup fix (was dropped; now back in scope)

**History, so it doesn't get lost again.** The architect's v0.99.1 review raised this
as a non-blocking finding. Alain dispositioned it on 26 Jul as *"folds into v0.99.2"*.
It never reached the v0.99.2 spec — verified absent 1 Aug. Alain restored it to scope
on 5 Aug ("refTrack fix, make it back"). It is small; it is here because it was lost
once already.

**The defect.** `hasUnbackedBlobs` (`src/lib/driveBlobPolicy.js`) decides whether a
metadata-only (`json`) push must escalate to `full` by testing **key presence** in
`manifest.driveFileIndex`. That is correct for the three immutable stores, where new
content always means a new key. It is wrong for **`refTracks`**, the one store that
**overwrites the same key** (`uploadRefTrack` keys by `itemId`,
`src/state/useEtudesState.js`). So: replace a reference track while the Drive token is
dead → the key is already in the index → no escalation → the 10-minute `json` push
skips it → the **old** file stays on Drive as the backup and the new content is not
uploaded until some *other* blob write triggers a full push.

**Window.** Narrow — auto-backup on, token dead, a refTrack replaced, and no other blob
written afterwards. Low severity; self-heals on any later full push. Worth fixing
because it is silent, and because the whole point of v0.99.1 was that backup stops
lying about what it has.

**Fix — two touches, no schema, no manifest shape change.**

1. **Invalidate the hash on write.** When a refTrack blob is written (the
   `uploadRefTrack` success path), clear that namespaced key from the manifest's
   `driveBlobHashes` — the stored hash no longer describes the blob under that key.
   Use the existing additive `writeDriveManifest` path; do not introduce a new field.
2. **Teach the escalation predicate about mutable stores.** In `hasUnbackedBlobs`,
   a `refTracks` key counts as *unbacked* when it has **no stored content hash**, in
   addition to the existing missing-file-index test. Immutable stores keep the current
   key-presence test unchanged. Keep the helper pure and cheap — **no hashing inside the
   escalation check**; the hash is computed in the full push where it already is
   (`shouldSkipBlobUpload`).

Net effect: replacing a reference track marks it unbacked, the next `json` push escalates
to `full`, `shouldSkipBlobUpload` finds no matching hash, the new content uploads, and the
fresh hash is recorded. Unchanged: the immutable-store fast path (no IDB read, no hash),
and every other escalation reason.

**Tests (extend `driveBlobPolicy.test.js`).** A refTrack key present in the file index but
with no stored hash → `hasUnbackedBlobs` true. Same key with a matching hash → false.
Immutable-store behaviour byte-for-byte unchanged. Hash invalidation clears only the
target key.

**Checklist item** (already written into `docs/manual-test-checklist.md`, v0.99.1
section): *replace a reference track while Drive is disconnected, reconnect, let a
scheduled backup run — the **new** content reaches Drive, not the old file.*

## A2 — How v0.99.2 is verified (settles the "hard merge gate" question)

The original spec made a two-device matrix a hard merge gate. Alain retired per-release
device passes on 26 Jul in favour of one pre-beta week; the 2 Aug quarterly then removed
the launch date the gate was protecting ("scoping, not dating"). Architect's advice,
accepted 5 Aug:

**Merge on tests + architect review** — this is not a data-loss gate (no users but Alain;
file backups exist). **But it is the one release where a defect is expensive to unwind**,
because merge semantics and a **one-way** schema migration land together. So two cheap
insurances, both required:

1. **A file backup taken immediately before the v0.99.2 deploy.** Not optional; it is the
   undo.
2. **Three checks run within ~1 hour of merge**, not deferred to the pre-beta week —
   newest-wins in both directions, tombstones stick, stamps don't drift on re-sync. They
   are marked ★ in the checklist. Everything else in the v0.99.2 section batches normally.

Report the migration triad result explicitly; a migration defect found after real state
has migrated is the one outcome this release cannot shrug off.
