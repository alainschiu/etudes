### v0.99.1 "Drive backup continuity" (~5–6 days)

**1.1 — Journal push stops embedding blobs (finding 1).**
`driveSync.js:188` calls `buildFullJournalPayload(opts.slice, opts.lsGet)`; the builder unconditionally base64-embeds all four stores (`journalPayload.js:33–56`). Mechanism: third param `opts` on the builder — `buildFullJournalPayload(slice, lsGet, {includeBlobs=true})`; when false, `blobs` key omitted entirely. `pushToDrive` passes `{includeBlobs:false}`. **Two callers total** (`driveSync.js:188`, `useImportExport.js:341`) — file export keeps the default. Restore compatibility: `applyJournalPayload`'s embedded loops iterate `data.blobs?.…` maps — a blob-less journal no-ops them (verify the optional-chain guards during implementation); **old journals with embedded blobs restore unchanged through the same path**. Fresh-device restore of a refs-journal already works by the existing mechanism: `restoreBlobsFromDrive` collects refs from state *metadata* (`collectJournalBlobRefs`), not from embedded blobs, and downloads the separate Drive blob files via `driveFileIndex`. The conflict-check pull (`driveSync.js:302–305`) automatically becomes cheap, as does the `JOURNAL_PREV` rotation copy (`:185`).
**Hard prerequisite discovered in code — the blob-coverage gap (G1, §6.1):** blob files reach Drive **only** in `'full'` pushes; a user whose activity only ever triggers the 10-minute `'json'` interval has *no* separate blob files — today the embedded journal is their accidental safety net, and 1.1 removes it. 1.1 must therefore ship **with** coverage detection: on every `'json'` push, cheap set-difference `idbAllKeys(store)` vs `manifest.driveFileIndex` keys; any missing → escalate that push to `'full'` (the existing `coalesceFull` flag is exactly the right hook, `driveSync.js:49,162`). No hashing needed for this check.

**1.2 — Drive session survives relaunch (finding 2).**
Verified: token in module memory (`driveAuth.js:37–39`), all interactive paths hardcode `prompt:'consent'` (`:153,187`), nothing re-acquires at boot, and the auto-backup interval's deps (`useDriveSync.js:68`) never re-evaluate `hasDriveToken()` — one teardown at mount, never retried. Mechanism, four parts:
- **Device-local connected marker:** additive manifest fields `driveConnectedAt` (ISO) + `driveAccountEmail` (from the `about?fields=user` probe), written on successful connect, cleared on disconnect. **Not** `settings.driveConnected` — that flag syncs via Supabase and pollutes other devices (G2, §6.2).
- **Boot silent reconnect:** in `App.jsx` boot (alongside the existing `prepareDriveAuth()` effect, `App.jsx:57`): if `isDriveConfigured() && readDriveManifest().driveConnectedAt` → attempt silent renewal via a **new wrapper** `silentRenewWithTimeout(ms=10000)` (wraps `getDriveAccessToken({interactive:false})` with an external timeout — the silent path currently has none, G4; the wrapped function itself is untouched, honoring the CLAUDE.md invariant). Success → token cached, emit token event; failure → quiet, Sync tab offers Reconnect. No UI may pop from boot (NS + iOS gesture invariants).
- **Reactive token state:** `driveAuth.js` gains `subscribeDriveToken(cb)` — emitted on acquire/expire/clear. `useDriveSync` subscribes into a `tokenEpoch` state included in the interval effect's deps (`useDriveSync.js:54–68`) and in `notifyBlobWrite`'s gate — auto-backup resumes the moment a token exists, stops when it dies. `isDriveConnected` export becomes reactive the same way (Sync tab display).
- **Consent-free reconnect:** interactive paths take a `prompt` argument; first-ever connect (no `driveConnectedAt`) keeps `'consent'`; reconnect uses `''` (Google shows its own chooser only when needed). `requestDriveTokenInteractive`'s synchronous-gesture contract and 12s timeout are preserved verbatim (iOS invariant).
Edge cases: Safari ITP can fail silent renewal with third-party-cookie blocking — the failure path must be quiet + recoverable (Reconnect button), never a boot popup. Multi-account: `driveAccountEmail` shown in the Sync tab so a reconnect to the wrong account is visible.

**1.3 — Full push skips already-uploaded blobs (finding 3).**
Verified: `driveSync.js:202–239` re-uploads (`driveMediaUpdate`) every blob every full push. Key code fact: **three of the four stores are immutable per key** — pdfs (new file = new `libraryId`), recordings, pieceRecordings (key embeds `Date.now()`); only **refTracks overwrite the same key** (`uploadRefTrack` keys by `itemId`, `useEtudesState.js:545`) (G3). Mechanism, per-store policy: for immutable stores, `driveFileIndex[ns]` existing ⇒ **skip entirely** (no API call, no hashing); for refTracks, SHA-256 (`crypto.subtle.digest`, sequential, one blob in memory at a time) against additive manifest map `driveBlobHashes:{ns:hex}` — upload only on mismatch. Accepted trade (record it): a blob deleted Drive-side while its index entry survives will not re-upload until restore surfaces it in `failed[]`; mitigation deferred (a "verify backup" action is a natural v0.99.5+ item).

**1.4 — Drive-restore confirm gains the inventory (finding 7-Drive).**
Today `modals.jsx:168` confirms *before* anything is fetched, blind. Post-1.1 the journal is small, so: button → busy → `pullJournalFromDrive` → build inventory from `remoteState` → destructive confirm with the same content as the file-restore confirm (items/routines/history/notes/blob counts + local-tz date) → apply on confirm. Mechanism: extract the inventory block at `useImportExport.js:538` into a pure `summarizeJournal(payload)` in `src/lib/journalSummary.js`, consumed by file-restore confirm, Drive-restore confirm, **and v0.99.2's conflict modal** (deliberate shared foundation). Edge: explicit restore continues to bypass the `needsPrompt` conflict heuristic (user already chose direction); blob-restore progress/failed counters unchanged.

### v0.99.2 "Multi-device merge" (~6–7 days)

**2.1 — `updatedAt` stamping (items, programs, routines; notes already stamped).**
The hard part is *where*: `setItems` has dozens of inline updater call sites (spots, performances, noteLog, bookmarks…) — per-site stamping is the error-prone path. Mechanism: **single choke point** — wrap each list's setState at its definition:
```js
const [items,_setItems]=useState(…);
const setItems=useCallback((updater)=>_setItems(prev=>{
  const next=typeof updater==='function'?updater(prev):updater;
  if(applyingCloudRef.current)return next;          // cloud apply: never re-stamp
  return stampChanged(prev,next);                    // ref-diff: prev[i]!==matching next el → {...el, updatedAt:Date.now()}
}),[]);
```
`stampChanged(prev,next)` (pure, `src/lib/merge.js`, vitest): id-indexes `prev`, stamps only elements whose reference changed or are new; deletions pass through untouched. All existing call sites keep working unchanged. Same wrapper for `setPrograms`, `setRoutines`. **`applyingCloudRef` judgment (asked):** sound for this purpose — it's set synchronously before the apply's `setState` calls and the wrapper reads it *inside the updater* (executes synchronously during those calls), so the guard cannot race; the `requestAnimationFrame` clear only matters for the *persist/dirty effects*, which also run before rAF fires. One hole: the dev-only seed path and `applyJournalPayload` also call setters — both already run under `applyingCloudRef` or must be set to (audit all `applyingCloudRef.current=true` sites during implementation).
**Reflections** (locked into scope): `dailyReflection` is a bare string; week/month are `{notes,goals}` — changing shapes would touch 13 writing surfaces. Mechanism instead: parallel meta key `etudes-reflectionMeta = {daily:ts, week:ts, month:ts}`, stamped in the three setters' wrappers (same choke-point pattern), synced as part of state, used only by merge. No surface changes.

**2.2 — Tombstones.**
New state key `etudes-deletions`: `[{kind:'item'|'program'|'routine'|'note', id, at}]`, appended by the four delete paths (`deleteItem` incl. its undo-toast finalization — tombstone written when the trash actually commits, *not* on the undoable click; `deleteNote`; program remove; routine delete). Pruned >90 days at the daily-rollover check. Included in `coldState` (syncs), in export payload, in v13 migration defaults.

**2.3 — `mergeStates` newest-wins + tombstones (`sync.js:10–41`).**
Per-id lists (items/programs/routines/freeNotes): both sides have the id → higher `updatedAt` wins; missing-vs-missing or missing-vs-present `updatedAt` → **local wins** (today's behavior; migration-tolerant, prevents pre-v13 clients' data being steamrolled). One-side-only ids → union, **unless** a tombstone with `at > entity.updatedAt||0` exists → drop (delete wins over stale copy; edit-after-delete keeps the entity and drops the tombstone — resurrection is *deliberate* when the edit is newer). Deletions lists union+prune. Reflections: `reflectionMeta` timestamps decide scalar direction per reflection. Settings/history: **unchanged** (not in the locked scope — flagged §6.8). `structurallyEqual` already ignores `updatedAt` (shipped v0.98.6) — `deletions` and `reflectionMeta` must be added to the sign-in overlap check's blind spots review, though the check at `useEtudesState.js:650` compares items only, so no change strictly required. Merge stays a pure `lib/sync.js` function — Drive can consume it later (locked direction) with zero coupling added now.

**2.4 — Informed conflict modal (finding 6).**
`SyncConflictModal` gains two summarized columns from `summarizeJournal`-style helper `summarizeState(local, remote)`: entity counts, newest `updatedAt` per side (relative time), local `localDirtyAt` vs remote `updated_at` from `loadFromCloud` (already returned, `sync.js:58`, currently discarded by the caller — thread it through `useEtudesState.js:603ff`). Buttons unchanged (Merge / Keep local / Keep cloud) — merge is now newest-wins so its label copy should say so (house voice, e.g. *"Merge — newest edit wins"*).

## §2 Migration plan (v13)

- `SCHEMA_VERSION=13` (`config.js`). Live-load (unconditional idempotent, house pattern): `migrateItems`/`migratePrograms`/`migrateRoutines` pass `updatedAt` through when present, **do not default-stamp** (absent = unknown = 0 in merge comparisons — mass-stamping at migration would fabricate recency and let a freshly-migrated device steamroll genuinely-newer edits from an unmigrated one). New keys default: `deletions:[]`, `reflectionMeta:{}` — loader `lsGet` defaults, no marker needed (additive shape).
- `IMPORT_MIGRATIONS {from:12,to:13}`: identical treatment for import/Drive payloads (shares the live helpers, house pattern from v11/v12).
- **Cross-version sync window:** a v12 client and v13 client sharing one Supabase account — v12's `mergeStates` ignores the new fields but round-trips unknown keys?? **No — it doesn't**: `applyCloudState` (`useEtudesState.js:564+`) rebuilds state field-by-field, dropping `deletions` on the old client, and its next push omits them. Accepted: single-user app, upgrade lag is hours (PWA prompt); risk = tombstones lost if an old client pushes between migrations. Record as a known, bounded limitation in the PR (same class as every prior schema bump here).
- Triad tests: fresh / v12-with-data / empty, idempotency double-run, import chain 1→13.

## §3 Timer-sync fix design (the every-second trap, addressed explicitly)

**Reframing the finding from code:** `syncStateRef` *includes* `itemTimes`/`restToday` (`useEtudesState.js:200`), and `doSync` fires on `stopItem`, `closeDay`, tab-hide, and network-online (`:319,337,680`) — so timer seconds *do* reach the cloud on most session ends. The real defect chain is: the **dirty marker** effect (`:132`) excludes them → after a timer-only session + reload, the sign-in conflict check (`:635-663`, runs on every boot via `signInEpoch`) computes `localDirty=false` → takes the silent **apply-remote** path → `applyCloudState` overwrites local `itemTimes` with the stale cloud copy. **Loss by clobber, not by never-pushing.**

**Design (no per-second writes anywhere):**
1. **Dirty on transitions:** `startItem`, `stopItem`, `toggleRest`, `editItemTime`/`editSpotTime` stamp `etudes-localDirtyAt` once (they're discrete user actions).
2. **Dirty heartbeat during long sessions:** the existing 60-second rollover interval (`:297`) additionally stamps dirty **iff** `activeItemId || isResting` (read from `rolloverRef`, already refreshed each render). One localStorage write per minute max, zero new intervals, zero render churn.
3. **Push heartbeat (crash insurance):** same 60s tick, `if timer-active && user && Date.now()-lastSyncedAt > 5min → doSync()` — bounds loss from a killed PWA to ~5 minutes of seconds. Uses refs; no effect-dependency changes.
4. **`pagehide` listener** added beside the existing `visibilitychange` handler (`:680`) — iOS Safari termination path doesn't reliably fire `visibilitychange`.
5. **Explicitly rejected:** adding `itemTimes` to `coldState` or the dirty effect's deps — `coldState` memo would rebuild every second and the 5s-debounce auto-sync (`:678`) would fire continuously through every practice session. That is the trap the brief warns about; the design above never touches those deps.

## §6 Pushback / flags (for comparison — flagged, not decided)

1. **G1 — Blob-coverage gap must ride 1.1 or beta risk *increases*.** Removing journal embedding deletes the only blob path json-only users have. My scope couples coverage-escalation to 1.1; if the architect's spec doesn't, this is the highest-priority reconciliation item.
2. **G2 — `settings.driveConnected` is synced state** (set in `useDriveSync.js:73`) and therefore lies on every other device. My design keys off a device-local manifest marker and treats the settings flag as display-legacy; its long-term fate (migrate/remove) should be an explicit architect call.
3. **G3 — refTracks are mutable per key** (`uploadRefTrack` overwrites `itemId`); a uniform existence-skip in 1.3 would silently stop backing up replaced reference tracks. Per-store policy proposed; needs architect confirm.
4. **G4 — the silent token path has no timeout** (`driveAuth.js:174-200`, unlike the interactive 12s at `:158`) — a hung GIS iframe would hang boot reconnect forever. Wrapper proposed; new work not in the brief.
5. **Finding 5-aggravator reframed:** timer seconds mostly *do* push (stop/day-close/tab-hide all call `doSync` with `itemTimes` included); the loss is the **boot-time conflict clobber** via the dirty-marker gap. Same fix list, different mechanism — worth aligning the spec's wording so the acceptance test targets the clobber (§3 acceptance), not "never syncs".
6. **Manifest snapshot omission risk:** any new manifest fields (1.2, 1.3) must be added to `manifestSnapshot()` (`driveSync.js:59-68`) and the restore mapping (`:337-343`), or a fresh-device manifest restore silently drops them. Easy to miss; called out so both specs cover it.
7. **`applyCloudState` drops unknown fields** — it rebuilds state field-by-field, so v13's new keys must be added there (`useEtudesState.js:564+`) *and* to `coldState`/export/`applyJournalPayload`; a checklist item in the v0.99.2 PR.
8. **Out-of-lock candidates observed, not scoped:** `settings` and `history` merges keep today's semantics (remote-wholesale / local-wins-per-key). If newest-wins is wanted there, it's a scope addition — flag only.
9. **`maybePullOnOpen`/Sync-tab pull** stays gated on token — after 1.2 it works across relaunches automatically; no separate fix needed (noting so it isn't double-scoped).
10. **Minor, same-class:** UTC `slice(0,10)` also at `useImportExport.js:478` (ZIP recording filenames). Cosmetic; batch with 0.4 or drop.
11. **Homeless-items check (standing instinct):** nothing new beyond the resolved context patch. The v0.98.9 rolling device-pass list and PDF Tier-3 items remain parked in the v0.99.5+ band per the patch.
